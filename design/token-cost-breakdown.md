# 简单任务的 token 去向拆解

日期：2026-10-29
数据：`.tmp/quality-cn-fixed`（8 个基础任务 × 1 轮，CN 渠道 `cn:deepseek-v4.1-flash`）
工具：`node scripts/token-breakdown.mjs .tmp/quality-cn-fixed`

## 为什么要拆

`quality-cn-deepseek-baseline.md` 记着「简单任务也用了 4.1 万至 6.3 万累计 token」，但只有总数，
说不清是主线回合太重、辅助请求太多，还是重复读取在放大。不拆开就不知道该优化哪一段。

## 口径

纯离线统计 trace（`**/.haji/traces/*.events.jsonl`），不调用任何模型：

- `llm_call` 事件带完整 messages 与 usage，按提示词特征分类：
  - **mainline**：`messages[0].role === "system"` 且 system 以 `# 身份与目标` 开头（主线回合的固定身份段）；
  - **title**：会话标题请求（`请针对以下用户的第一条需求，总结出`）；
  - **compaction / distill**：压缩摘要、经验提炼（按提示词特征）；
  - **other**：短请求但没命中特征——出现即说明有新辅助请求需要补特征，先落这里而不是算进主线。
- 主线必须先判，否则主线 system prompt 里本来就写着「压缩」「摘要」，关键词会把主线全吃掉（第一版脚本踩过）。
- 重复读：同一会话内 `read` 的 `path + 行范围 + symbol` 完全相同的第 2 次及以后。

## 结果

| 会话 | 请求 | 主线 token | 辅助 token | 重复读 | 工具调用 |
| --- | ---: | ---: | ---: | ---: | ---: |
| chunk | 8 | 57,523 | 235 | 1 | 7 |
| clamp | 7 | 46,096 | 186 | 1 | 5 |
| median | 8 | 56,012 | 323 | 1 | 6 |
| parse | 8 | 57,463 | 243 | 1 | 7 |
| range | 8 | 56,115 | 265 | 1 | 7 |
| rename | 7 | 46,949 | 246 | 2 | 7 |
| sum | 8 | 54,471 | 178 | 1 | 6 |
| unique | 8 | 54,629 | 176 | 0 | 6 |
| **合计** | **62** | **421,519 + 7,739 输出** | **2,155** | **8** | **51** |

- 主线占 **99.6%**，辅助请求（标题）只占 0.4%；这批短任务里没有触发压缩与经验提炼，`other` 为 0。
- 主线平均每次请求 **输入 7,806 token、输出 143 token**，每任务约 7 次请求。
- 输入缓存命中 **84.3%**，未命中缓存输入共 **66,319 token（15.7%）**——与 A/B 报告里的
  「未命中 token / 会话 27,865」同量级（那边是 2 轮会话）。
- 重复读每会话 0–2 次，合计 8 次，不是主要成本项。

## 结论

1. **辅助请求不是问题**。标题请求 8 次共 2,155 token（0.4%），压缩与提炼在这类短任务里根本没触发。
   想省 token 不必先去动辅助模型。
2. **成本结构是「请求数 × 单次 prompt」**：每任务 7 次请求、每次 ~7.8k 输入，其中约 7.1k 是
   身份段 + 工具面 + 经验召回组成的固定前缀，其余是随回合增长的历史。总输入 421.5k 里
   固定前缀重复了 54 次，靠 84.3% 的缓存命中把实际计费压到 66.3k 未命中 token。
3. **因此优化优先级**：减少请求数（把「读文件→改→验证」压成更少的回合、减少无谓的只读调用）
   ≫ 缩短固定前缀 ≫ 动辅助请求。固定前缀已经命中缓存，缩它的收益主要落在首次请求和缓存失效时。
4. **重复读不是瓶颈**（每会话 ≤2 次），不值得为它加机制；`read_symbol` / `read_outline`
   这类「少读一点」的收益也要按这个基数折算——单次读省几百 token，相对 7.8k/次 的输入占比很小。

## 复现

```bash
pnpm run build                       # trace 由 dist 产出，先构建
node scripts/token-breakdown.mjs .tmp/quality-cn-fixed
node scripts/token-breakdown.mjs .tmp/quality-cn-fixed --json   # 机器可读，便于对比两轮
```

对比两轮（例如改完请求数之后再跑一遍）：同一目录结构跑两次，比 `mainline.requests` 与
`promptTokens - cachedTokens`（未命中输入）两项即可；总 token 会因缓存命中率波动，别只看总数。
