# read_outline：read 截断时附「剩余符号提纲」

日期：2026-10-27
数据：`data/2026-10-27-read-outline-pilot.json`（24 个会话，4 任务 × 3 轮 × 2 arm）

## 假设

单文件 `read` 被截断时只给 `nextStartLine`，模型只能一页页往后翻。全量 trace 里
单文件 read 有 71% 被截断、70% 是 `startLine > 1` 的续读；续读中只有 33% 是顺序翻页，
29% 是远跳、38% 是回跳/小间隔。也就是说，**「给剩余区间的符号 + 行号」比「加大单次额度」更对症**：
模型可以直接用 `aroundLine` 跳到目标位置，而不是多翻几页。

## 改动

`read` 在本页之后还有内容时，头部多一行：

```
[剩余符号] 262 fn main · 386 fn hasCustomProviderKey · 557 fn withModelMeta · … · 3100 fn pricingLookupUrls
```

- 只扫 `actualLastLine+1` 之后的区间；`aroundLine` 是模型明确指定的窗口，不附提纲。
- 轻量正则扫描（TS/JS、Python、Go、Rust、JVM/Kotlin、Markdown、Shell），不引入 AST；
  未知扩展名不输出。
- 条目 >24 时按行号均匀抽样（保留首尾），字符上限 600；超出时保留远端锚点或至少加 `…`。
- **只在单文件读时附提纲**，不缩减正文；批量读不附（单块额度小，提纲会挤占正文）。
- 实验开关：`HAJI_EXPERIMENTS="read_outline=baseline|outline"`，首轮 pilot 后默认 `outline`。

## 方法

- 任务：3（会话保存链路）、5（`createToolCallBatches` 调用链）、7（工具错误分类与止损）、
  9（`packages/core/src` 文件职责）。
- 每个任务 3 轮，每轮 baseline / outline 各一次，交替执行；共 12 对。
- 只改 `read_outline`，其余实验保持默认；`--no-worktree`，只读任务。
- 1 个 outline 会话在服务重启时被中断，已从数据中剔除；另补跑一次同任务同 arm。
- 指标口径见 `scripts/ab-metrics.mjs`；费用按官方人民币高峰价。

### 质量抽查

四个任务的关键结论词（如 `saveCurrentSession`/`flush`、`createToolCallBatches`/`turn-runner`、
`RepeatedFailureTracker`/`noop`/`concurrent`、`session-manager`/`context-compact`）在
**两臂的全部 24 次运行里都命中**；completion token 在 outline 侧持平或更低
（任务 7：7.1k → 5.2k，任务 9：1.6k → 1.4k）。没有看到「提纲让模型少读关键文件」的迹象。

## 结论

**首轮 pilot 正向**：请求 −12.9%、未命中 token −12.2%、费用 −14.0%，中位墙钟 −16.9%；
剔除一个未触发提纲的离群会话后总墙钟 −11.0%。收益来自「少翻页、少请求」，不是省缓存 token
（缓存命中率基本不变）。

**已按首轮 pilot 切为默认 `outline`**（`baseline` 保留为对照组）。

**数据范围**：本报告只覆盖任务 3/5/7/9 × 3 轮 × 2 arm（24 会话），不是全量 11 任务；
按当前结论直接采纳，不再补确认轮。如果以后需要复核，重点看：

- 请求数与未命中 token（主指标），墙钟看中位数而不是均值；
- 任务 5 这类「读得少、提纲用不上」的场景是否继续中性；
- 提纲触发率（本次 outline 会话 96 次 read 里 40 次带提纲，其余是批量读/`aroundLine`）。
