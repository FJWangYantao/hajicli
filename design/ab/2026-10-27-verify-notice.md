# post_edit_verify_notice：验证通过时要不要回注提示

日期：2026-10-27
数据：`data/2026-10-27-verify-notice.json`（3 任务 × 2 arm × 2 轮 = 12 次运行）
脚本：`write-bench/run.sh`（`ALT_CLI=<对照构建>/dist/index.js`）

## 背景

上一轮（`2026-10-27-write-edit-forced.md`）在任务 2 上发现：修好探测后验证能在 0.7 秒内
跑完并回注「[编辑后验证] … 通过（未发现错误）」，但 4/4 轮都比「超时不回注」更慢
（墙钟 +36%、请求 +15%）。机制解释是：这条消息没有让模型少自检（两臂都自己跑了 1 次
`tsc`），只是给每个验证窗口多加一条上下文消息。

于是把成功提示去掉——只在**发现问题**时回注——再验一次。

## 方法

- 两臂是**两个二进制**（代码只差这一处，用 `ALT_CLI` 指向预构建的对照）：
  - `notice` = 改动前（HEAD 构建，成功也回注）；
  - `quiet` = 改动后（`result.ok` 时返回 `undefined`）。
- 任务 1（加函数 + 测试）、2（跨文件重命名，已强制走 edit）、3（修边界 + 回归测试），各 2 轮。
- 两臂共用同一 worktree 流程、同一 HOME、同一份 instincts。

## 结果

正确性：**12/12 全对**（`tsc -b` 通过、测试通过、重命名无残留）。

| 指标 | notice | quiet | 变化 |
| --- | ---: | ---: | ---: |
| 墙钟 / 次 | 57.8s | 60.3s | +4.3% |
| 请求 / 次 | 15.3 | 14.2 | −7.6% |
| prompt token / 次 | 156,008 | 150,896 | −3.3% |
| 未命中 token / 次 | 8,915 | 10,907 | +22.3% |
| completion token / 次 | 3,195 | 3,016 | −5.6% |

逐轮（墙钟秒）：

| 任务 | notice | quiet |
| --- | ---: | ---: |
| 1 加函数 | 34 / 39 | 36 / 59 |
| 2 重命名 | 75 / 65 | 92 / 90 |
| 3 修边界 | 61 / 73 | 32 / 53 |

6 对里 quiet 更快 3 对、更慢 3 对——**完全分不开**。

## 结论

1. **上一轮「成功提示净负收益」不成立**：同一任务 2 上，quiet 反而比 notice 慢（92/90 vs 75/65），
   方向翻了过来。也就是说那次 4/4 一致只是小样本巧合（每格 n=1–4，任务间方差 30–90 秒）。
   已在 `2026-10-27-write-edit-forced.md` 的结论里标注。
2. **改动本身仍然保留**：请求 −7.6%、prompt token −3.3%，方向符合机制（少一条消息），
   且不损失任何正确性；但它只是几个百分点的量级，**不是墙钟层面的优化**。
3. **方法论教训**：写路径单次运行方差 30–90 秒，n=2 的配对根本分辨不出 <20% 的差异。
   写路径实验要么每格 ≥5 轮，要么只测「机制是否发生」（工具选择、注入次数），别拿墙钟下结论。
