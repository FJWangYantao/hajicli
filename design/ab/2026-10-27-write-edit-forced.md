# write_path_edit_forced：强制走 edit 的写路径对照

日期：2026-10-27
数据：`data/2026-10-27-write-edit-forced.json`（任务 2 × 2 arm × 4 轮 = 8 次运行）
脚本：`write-bench/run.sh`

## 为什么重跑

首轮基准（`2026-10-27-write-baseline.md`）里，任务 2「跨文件重命名」在 old 臂用
`sed -i` 一条 bash 完成，`post-edit-verify` 一次都没触发——测的是 sed 而不是 edit 路径。

这次做了两件事：

1. 任务 2 的提示加硬约束：**必须用 edit 逐处修改，禁止 sed/perl/python 写文件**；
2. `run.sh` 增加工具用法审计（从 trace 数 `edit` / `write` / bash 写文件次数），
   口头约束不算数，必须拿 trace 核实。

结果：**8/8 次运行全部走 edit（7–10 次），bashWrite = 0**。审计口径现在能区分两臂，
脚本还修掉一个 bug：`cp -r` 到已存在的 trace 目录会嵌套一层，导致读到上一次的数据。

## 方法

- 两臂是同一份代码，只差验证命令：
  - `old`：`HAJI_POST_EDIT_VERIFY="npm run check --silent"`（15 秒超时，超时**不注入**上下文）；
  - `fixed`：默认探测 `npx tsc -b`（约 0.7 秒，成功也注入「验证通过」）。
- 每次独立 worktree + `pnpm run build` 预热，`--permission-mode bypass-permissions`，
  跑完做正确性检查（`tsc -b` 通过 + 旧名无残留）。

## 结果

正确性：**8/8 全对**（`tsc -b` 通过、重命名无残留），两臂没有差别。

| 指标 | old | fixed | 变化 |
| --- | ---: | ---: | ---: |
| 墙钟 / 次 | 68.5s | 93.0s | **+35.8%** |
| 请求 / 次 | 17.8 | 20.5 | **+15.5%** |
| prompt token / 次 | 205,000 | 237,203 | +15.7% |
| 未命中 token / 次 | 16,904 | 17,363 | +2.7% |
| 费用 / 次 | ¥0.0770 | ¥0.0804 | +4.5% |

逐轮（墙钟秒）：

| 轮次 | old | fixed |
| --- | ---: | ---: |
| 1 | 87 | 90 |
| 2 | 45 | 63 |
| 3 | 80 | 105 |
| 4 | 62 | 114 |

**4/4 轮 fixed 都更慢**，方向一致，不只是均值被离群点拉动。

## 关键观察

1. **「验证通过」提示没有让模型少跑验证**：两臂每个会话都自己跑了 1 次 `tsc`
   （fixed 臂有两轮跑了 2–3 次），也就是模型不信任/不依赖这条提示，仍按自己的习惯自检。
2. **所以这条提示只剩成本**：每个验证窗口（10 秒冷却）多一条 system 消息，上下文变长、
   请求数上去。任务 2 是纯机械改名，`tsc -b` 永远通过，注入的信息量为零。
3. **15 秒超时不阻塞回合**：old 臂的超时提示只进界面不进上下文，模型该干嘛干嘛，
   所以「修好探测、把验证从 15 秒缩到 0.7 秒」在机械改动上换不来墙钟收益。

## 结论

**任务 2 这类机械改动上，成功提示是净负收益**：墙钟 +36%、请求 +15%、费用 +4.5%，
正确性没有区别。而早先基准里 fixed 在任务 1/3（新增代码、修边界）上明显更快，
说明价值取决于「验证是否真的发现问题」。

> **2026-10-27 追加**：按此结论去掉成功提示后重跑（`2026-10-27-verify-notice.md`），
> 同一任务 2 上方向反转（quiet 92s/90s vs notice 75s/65s），3 任务 × 2 轮 6 对里 3 胜 3 负。
> 也就是说本轮「4/4 一致更慢」**没能在更大样本上复现**，应视为小样本巧合，不要引用这里的
> 墙钟幅度。改动本身仍保留（请求 −7.6%、prompt token −3.3%，机制上更省），但量级只有几个百分点。
